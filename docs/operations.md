# Operations runbook — repo

Every command below is for the stack that was generated here. Where a step depends on
something EgyKode Pilot could not verify, it says so rather than guessing.

## Deploying a change

Merge to `main`. The CD workflow plans the infrastructure for that commit and, when the
plan changes something, applies it in the `production` environment, which waits for a
reviewer only if the repository's environment settings require one. It publishes each image,
registers a new task-definition revision of `repo-production` that names the image by digest, and
rolls the service onto it in the same environment. It then checks that the primary deployment
runs that revision and image, and that the application answers through its load balancer: a
release the deployment circuit breaker rolled back fails the run.

## Rolling back

Every release registers a new task-definition revision, and the earlier ones stay
registered, so the known-good release is still there to return to. Returning to it is an
operator's decision and a deployment like any other, and a stable service is not proof that it
runs what was asked for:

```bash
# What runs now, and the revisions before it
aws ecs describe-services --cluster repo-production --services repo-production \
  --query 'services[0].deployments[].[status,taskDefinition,rolloutState]' --output table
aws ecs list-task-definitions --family-prefix repo-production --sort DESC --max-items 5

# Return to the known-good revision, wait, then confirm the primary deployment runs it
aws ecs update-service --cluster repo-production --service repo-production \
  --task-definition repo-production:<known-good-revision>
aws ecs wait services-stable --cluster repo-production --services repo-production
aws ecs describe-services --cluster repo-production --services repo-production \
  --query 'services[0].deployments[?status==`PRIMARY`].taskDefinition | [0]' --output text
```

The worker is its own service: repeat for `repo-production-worker`, its service and task family, in
the same cluster.

This changes what runs, not the repository, so the next merge to `main` deploys again. Keep
the rollback by reverting the change in Git and merging the revert, which is a new release
through the reviewed pipeline; reverting or resetting a commit on its own deploys nothing.

An image rollback is not a database rollback: a migration that ran with the bad release stays
applied. Roll the data forward, or restore a backup deliberately.

Infrastructure is a different question. `terraform apply` on an older commit is *not* a
rollback for anything stateful — a database whose `identifier` changed is replaced, not
renamed. Read the plan before applying it.

### When an infrastructure apply stops partway

Terraform records each resource in its state as it is created, so an apply that failed or was
cancelled leaves state that describes what now exists. Do not delete the state, or the
resources it lists, by hand.

1. Find the resource that stopped the apply in its log, and fix the cause.
2. Plan again by re-running the CD workflow: the plan starts from the recorded state and
   shows only what remains. Review it before it is applied.
3. A cancelled apply can leave its state lock held. Once you are sure no apply is running,
   release it from `terraform/` with `terraform force-unlock <lock-id>`; the error names the lock.

Nothing generated scales the service: it runs the count the estimate bills. Terraform
ignores the count after creating the service, so change it where delivery sets it —

## Rotating a secret

Secrets are not in this repository. They are read at runtime, so rotation is:

1. Change the value in the secret store.
2. Restart the service so it re-reads the value.
3. Restart the workloads that cached it.

Nothing in step 1 touches git. If a credential was ever committed, rotating it is not enough —
it is in the history until the history is rewritten.

## Removing the stack

No workflow here runs `terraform destroy`. Removal is an administrator's step, run by hand,
and it cannot be undone. In this order:

1. From `terraform/`, `terraform init -backend-config=backend.hcl -backend-config="key=repo/production/terraform.tfstate"`, and check `terraform state list` lists this stack's resources.
   If it lists nothing you are reading another state: stop, because the steps below would then
   delete the state of a stack that is still running.
2. The production database refuses deletion and keeps a final snapshot. In
   `terraform/main.tf`, set `deletion_protection = false` in the `database` module (and
   `final_snapshot = false` only if its data may go; a kept snapshot is billed until deleted),
   then `terraform apply -var-file=envs/production.tfvars` and review that plan: it changes only the database.
3. `terraform destroy -var-file=envs/production.tfvars`. Image repositories go with their images.
4. A few minutes later, look for `/aws/ecs/containerinsights/repo-production/performance`. Container Insights can write it again after
   Terraform has deleted it, and a group created then is outside Terraform and never expires:
   `aws logs delete-log-group --log-group-name /aws/ecs/containerinsights/repo-production/performance`
5. The bootstrap last, since the state lives in it, and only once the destroy above reported
   this stack's resources destroyed. Its state bucket refuses destruction (`prevent_destroy`)
   and keeps every version of the state: remove that `lifecycle` block, empty the bucket of
   every object version, then run `terraform destroy` in `terraform/bootstrap` with the
   variables it was applied with. A GitHub OIDC provider passed in as
   `github_oidc_provider_arn` is left alone; one the bootstrap created is destroyed.

KMS keys are not deleted at once: AWS schedules each for deletion after its 30-day waiting period,
and it can be cancelled until then. Remove the role ARNs from the repository secrets afterwards.
