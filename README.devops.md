### First deploy

The state bucket has to exist before Terraform can store state in it, so it is created once by
a separate root module that keeps its own state locally. This is the one step the pipeline that
depends on it cannot do.

```bash
cd terraform/bootstrap && terraform init
terraform apply -var github_repository=OWNER/REPOSITORY \
  -var github_oidc_subject_prefix="$(gh api repos/OWNER/REPOSITORY/actions/oidc/customization/sub --jq .sub_claim_prefix)"
# once per project and account, and again after Pilot updates it
```

It also creates the three roles the workflows assume through GitHub's OIDC provider, so no AWS
key is stored in the repository: one that plans, for a push to main or a pull request; one that
publishes images to this project's ECR repositories, for a push to main; and one that applies and
deploys, only from the repository's `production` environment.

Then set, from its outputs, two repository variables — `TF_STATE_BUCKET` from
`state_bucket_name` and `TF_STATE_KMS_KEY_ARN` from `state_kms_key_arn` — and three
repository secrets — `AWS_PLAN_ROLE_ARN` from `plan_role_arn`, `AWS_PUBLISH_ROLE_ARN` from
`publish_role_arn` and `AWS_DEPLOY_ROLE_ARN` from `deploy_role_arn`.

**Updating an existing stack.** Apply the bootstrap again after Pilot updates it: it may add the
workload boundary and the publish role, and it moves the pipeline roles to their IAM path
(`/pilot/<project>/pipeline/`), which replaces them — copy the three role ARNs from its outputs
into the repository secrets again before the next run. A stack first applied before Pilot used IAM
paths has its roles, policies and instance profiles at `/`. The next apply moves them to the
project path, replacing each one; the deploy role may remove the old ones (only those tagged with
this application). On EKS the cluster and its node group are replaced with their roles: apply that
upgrade with an administrator in a maintenance window, or set `iam_path = "/"` in the tfvars to
keep the roles where they are and apply changes to them with an administrator.

After that, infrastructure changes go through `.github/workflows/infrastructure.yml`.

A pull request touching `terraform/` publishes a **speculative** plan: it shows what the change
would do, and nothing applies it. Merging to `main` produces a **second** plan from the merged
tree and applies that one, once a required reviewer approves. The two are deliberately
different artifacts — the merged tree is not the branch, and applying the branch's plan would
apply something that was never on `main`. What approval gates is the post-merge plan, and it is
applied exactly as saved rather than re-planned.

**The approval is a repository setting, not something the workflow creates.** GitHub creates an
environment referenced by a workflow with no protection rules, so until a required reviewer is
configured on the `production` environment this applies automatically on merge. Configure it
before the first apply: Settings → Environments → production → Required reviewers.

Applying by hand is still possible and is a different thing — it skips the review and leaves no
record of what changed:

```bash
cd terraform
cp backend.hcl.example backend.hcl                             # paste the bucket name in
# production's own state key; backend.hcl's example key is another environment's.
terraform init -backend-config=backend.hcl -backend-config="key=repo/production/terraform.tfstate"
terraform plan -var-file=envs/production.tfvars
```

State is locked with a conditional write on the state object itself (`use_lockfile`), so
there is no DynamoDB table to create.
